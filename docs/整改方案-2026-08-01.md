# 遇见APP 整改方案（2026-08-01）

> 基于全量代码梳理（后端 31 controllers / 28 models / 18 services / 22 routes；前端 17 页面 / 1058 行单文件；根目录散落源码；部署/安全/测试现状），对项目从**架构、视觉、功能完整性**三个维度做体检，输出分优先级的整改路线。本文为评估报告，不涉及任何代码改动。

## 一、项目现状总评

### 一句话结论

**后端是一个功能堆叠非常充分的 130+ 接口工程**（扣款、任务、配额、审核、反欺诈、通话落库等核心逻辑大多真实存在且事务完整）；**前端只实现了约 23% 的接口调用**（30/130+），大量功能处于"后端有、前端空"的断头状态；**部署与安全存在高危隐患**（生产私钥/数据库密码已入库）。

### 各维度健康度评分

|---|---|---|
| 后端功能完备度 | ★★★★☆ | 接口层很完整，分层框架标准，但代码质量存在多处硬伤 |

## 二、架构问题与整改

### 2.1 【高危】当前未提交改动「已有会话标记」功能断链

**现状**：本轮正在做的"首页打招呼/发消息"改造（`public/js/yujian-app.js` 109/179/852 行已依赖 `u._has_conversation`），配套实现**加错了文件**：

- 前端运行时读的推荐接口由 `src/services/match.service.js` 提供，**该文件没有 `_has_conversation` 逻辑**（已 grep 验证，0 命中）；
- 新增的逻辑（`conversationSet` 批量预取 + `_has_conversation` 标记）写在了**根目录 `match.service.js`**——它不在任何 require 链上，是死代码（`server.js` 走 `src/` 版本，已验证）；
- 配套的 `src/models/Conversation.js` 新增 `batchExists` 方法，但**没有任何运行时代码调用它**。

**后果**：前端 `{{u._has_conversation?'发消息':'打招呼'}}` 条件恒为 false，按钮永远显示"打招呼"，无论是否已有会话。

**整改**：
1. 把根目录 `match.service.js` 的 `conversationSet` 预取 + `_has_conversation` 标记逻辑**合并进 `src/services/match.service.js`**（含 `Conversation.batchExists` 调用）；
2. 合并后**删除根目录 `match.service.js`**；
3. 部署后由前端验证：已有会话的用户按钮显示"发消息"，新用户显示"打招呼"。

> ⚠️ 根目录 `match.service.js` 与 `src/` 版还有**实质性分叉**（limit 20 vs 50、预取倍数、是否排除已喜欢/已匹配、降级阈值等），合并时**以 src 版为基准**，只把 conversation 相关逻辑移植过去，不要把整份文件覆盖。

### 2.2 【高危】根目录 8 个垃圾源码副本

**现状**：项目根目录散落 9 个"源码状"JS 文件，其中 8 个是无引用的遗留副本：

| 根目录文件 | 结论 | 与 src/ 关系 |
|---|---|---|
| `websocket-server.js` | ✅ **活代码**（server.js:432 require） | 唯一被引用的根目录源码 |
| `match.service.js` | ❌ 垃圾（已分叉，见 2.1） | 与 src 版实质分叉 |
| `Conversation.js` | ❌ 垃圾 | 与 src 版分叉（含无人调用的 batchExists） |
| `Message.js` | ❌ 垃圾 | 与 src 版分叉 |
| `Skip.js` / `User.js` / `upload.service.js` / `post.routes.js` | ❌ 垃圾 | 与 src 版逐字节一致 |
| `websocket-server-fixed.js` | ❌ 垃圾 | 被当前 websocket-server.js 取代的迭代中间态 |

**整改**：确认 `src/` 版为线上基准后，删除这 8 个文件。`git log --follow` 可保留历史。

### 2.3 【高】聊天消息发送/撤回双实现（最易漂移处）

**现状**：
- 发送：`chat.controller.js:232-303`（HTTP 回退，msgType 2/3/4/5/6 分支 + WS 推送）与 `websocket-server.js:237-376`（`handleSendMessage`）**逐段同构**；
- 撤回：`chat.controller.js:150-194` 与 `websocket-server.js:574-610` 各自实现。

**后果**：消息字段/类型/事件名改动需同步两处，极易漂移（历史上 `sender_nickname` 字段就只在一个版本里）。

**整改**：抽 `src/services/chat.service.js` 作为**消息发送/撤回的唯一业务入口**，HTTP controller 与 WS handler 都只做协议层转调。

### 2.4 【高】model→service 反向依赖

**现状**：`src/models/Conversation.js:160`、`src/models/Message.js:48` 在静态方法内 `require('../services/websocket.service')` 做实时推送，**违反依赖方向**（model 应是最底层）。

**整改**：将推送逻辑从 model 内移出，由调用方（controller/service）在写入完成后触发 WS 推送。

### 2.5 【中】内存降级方案割裂

**现状**：`utils/database.js` 提供统一降级开关，但降级落地严重不一致：
- **21 个文件**各自维护一份 `memoryStore`（`const memoryStore = new Map()`），Haversine 距离、内存过滤、slice limit 在每个 model 内重复实现；
- **8 个 model 无降级分支**（Wallet、Checkin、Gift、UserDailyQuota、Anniversary、ChatEnhance、IntimacyBadge、NobleLevel）——DB 挂时**核心付费链路（钱包/签到/礼物/配额）静默失效**；
- 降级是进程内状态，`ecosystem.config.js` 已预告 cluster 扩容，多实例时各实例内存数据不一致，降级方案整体失效。

**整改**：
1. 抽 `BaseModel`（或 `src/utils/memoryStore.js` 单例）收敛 21 份复制；
2. 补齐 8 个无降级 model 的降级或**显式声明"DB 不可用时该功能不可用"**；
3. 明确降级边界：仅单实例开发/演示可用，集群部署必须依赖 Redis 兜底。

### 2.6 【中】错误码体系两套并存

**现状**：
- `errorCodes.js` 定义了完整业务码（1001 AUTH_REQUIRED / 1301 AUTH_FORBIDDEN / 5201 RATE_LIMITED 等）+ `getDefaultMessage`，但 **auth/adminAuth/contentAudit/rateLimit 中间件全部手写裸 `res.status(...).json(...)`**，用 HTTP 码而非业务码——业务码体系基本空转；
- 存在靠中文 `err.message` 字符串匹配判断业务错误的脆弱模式（`match.controller.js:82` 的 `businessErrors` 数组）。

**整改**：中间件改用 `response` 工具 + `errorCodes.js`；废弃中文匹配，改抛带 code 的业务异常。

### 2.7 【中】websocket-server.js 单文件职责过载（648 行）

**现状**：鉴权、心跳、连接生命周期、8 种消息路由、3 种拦截策略（审核/反欺诈/拉黑）、离线消息、5 个通话信令、在线状态广播全部内联；`handleSendMessage` 单函数 139 行；`CONNECTION_TIMEOUT=45000` 定义了从未使用（心跳实际靠 `isAlive` 布尔而非时间差，与注释不符）；在 `startWebSocketServer` 内重复注册 `process.on` 全局监听且从不移除（热重启叠加）。

**整改**：拆 `handlers/chat.js`、`handlers/call.js`、`protocol.js`（事件常量表）、`heartbeat.js`；移除重复的全局监听；用 `lastPong` 时间差实现真实超时。

### 2.8 【低】其他

- 事件类型字符串散落 5+ 个文件，抽 `src/constants/wsEvents.js`；
- `executeQuery` 返回契约在 3+ 处各自手写解包，在 `utils/database.js` 内统一；
- 上传路由内联在 `server.js`（166/278 行），迁入正式 controller；
- `.env.example` 缺 `AGORA_APP_ID`/`AGORA_APP_CERTIFICATE` 等实际消费的变量；
- `call.service.js` require `agora-access-token` 但 **package.json 未声明、node_modules 未安装**（运行即落 mock token），要么补依赖要么把"模拟 token"改为显式 feature flag。

## 三、功能完整性问题与整改

### 3.1 【高危】6 类数据库表缺少建表脚本（数据不落库）

**现状**：以下 model 引用的表**全仓库 SQL 无 CREATE TABLE**，靠内存降级"兜底"不报错，但**数据不落库、重启即失**——功能看似存在实则假：

| Model | 缺表 |
|---|---|
| Intimacy.js | `intimacies`、`intimacy_logs` |
| Anniversary.js | `anniversaries` |
| IntimacyBadge.js | `intimacy_badges`、`user_badges` |
| UserDailyQuota.js | `user_daily_quotas` |
| Sticker.js | `stickers` |
| Topic.js | `topics`、`post_topics` |
| ChatEnhance / NobleLevel | `chat_backgrounds`、`quick_replies`、`dress_up_items`、`user_dress_ups`（建表在 `add_features_batch2.sql`，**是否在生产执行过未验证**） |

**整改**：写一个**幂等建表脚本**（`src/db/add_missing_tables.sql`，统一含 `add_features_batch2.sql` 与 `add_admin_features.sql`），验证生产已执行后落地。

### 3.2 【高】匹配主链路整体缺失（核心产品闭环）

**现状**：后端 8 个匹配接口（`like`/`skip`/`super-like`/`matches`/`unmatch`/`likes`/`undo`/`daily-quota`）完整，但前端只调用了 `recommend`。首页是"推荐列表 + 打招呼"，**没有喜欢/跳过/超级喜欢/撤销/匹配成功弹窗**。

**整改**：把首页改回卡片滑动或列表操作流：喜欢/跳过/超级喜欢（扣 10 金币）/撤销，展示今日配额，接入已存在的 `match_success` WS 处理。这是"遇见"类产品的**主链路**。

### 3.3 【高】礼物消息前端不落库（接收方不可见）

**现状**：`sendGift` 送礼成功后仅前端本地 push 一条 type=6 消息，**不经过 `chat/messages` 落库、不经 WS 广播**。接收方聊天页实时看不到礼物，下次拉列表也拉不到（`gifts/send` 不写 messages 表）。

**整改**：`gifts/send` 成功后通过 `chat/messages`（type=6）落库并 WS 推送，或在后端 `gifts/send` 内写 messages。

**连带问题**：`gifts` 表 schema 用 `image` 列，`init-data.sql` 插 `icon` 列，前端模板用 `g.icon` —— 三处不一致，礼物图标取不到。需统一。

### 3.4 【高】WS 消息类型不匹配

| 问题 | 现状 |
|---|---|
| 客户端 30s 发 `{type:"ping"}` | 服务端只处理 `pong`，`ping` 落 default 分支 → **类型不匹配**（功能可用但语义错） |
| `typing`/`stop_typing` | 服务端发送，前端**完全不处理** → 无"对方正在输入" |
| `online_status` | 服务端发送，前端不处理 → 会话列表在线状态从不更新 |
| `read_receipt` | 前端既不发也不处理 → 已读回执半废 |
| `gift_received` / `push_notification` | 服务端推送，前端未注册 handler |
| `call_initiated` / `call_error` / `ice_candidate` | 前端不处理，**没有任何 WebRTC 媒体协商代码** → 通话是假实现（见 3.5） |

**整改**：前端 `ping` 改 `pong`（或服务端加 `case 'ping'`）；补齐高价值事件（typing/online_status/read_receipt/gift_received）的消费；`push_notification` 决定接还是收。

### 3.5 【中】语音/视频通话仅壳

**现状**：通话记录落库是真实闭环（`call.service.js` 写 `call_records`），但前端通话是**纯 UI 壳**：`startCallMedia` 只 `getUserMedia` + 计时器，**无 RTCPeerConnection、无 ice_candidate 交换**，双方永远建不起媒体通道。前端也无 `/api/call/history` 入口。

**整改**：二选一——①接入真实 Agora + WebRTC（服务端已有 token 分支，配置 `AGORA_APP_ID` 即可）；②把通话 UI 隐藏或标注"敬请期待"。当前"界面能点、永远接不通"是最差状态。

### 3.6 【中】签到+任务系统前端零入口

**现状**：后端**闭环完整**（`Checkin.checkin()` 原子插入 + 发金币；`updateTaskProgress` UPSERT；6 个任务 5 个在代码里有触发调用）。前端没有任何签到/任务 UI，用户完全感知不到。

**整改**：前端加"签到领金币 / 今日任务"页（后端接口齐备，纯前端工作）。

### 3.7 【中】VIP/充值纯模拟支付

**现状**：`NODE_ENV=development` 或 `SIMULATE_PAYMENT=true` 时**点击即开通**，无任何支付流程；生产分支只返回 `payment_required` 订单号，无支付网关/回调。前端 `buy()` 直接 toast "开通成功"。

**整改**：产品要真实收费 → 对接支付网关 + 回调 + `orders/list` 页；仅演示 → UI 明示"模拟支付"。

### 3.8 【中】认证/拉黑/举报/推送四模块有后端无入口

**现状**：`verification/*`（实名/人脸/学历/车辆 6 接口）、`block/*`、`report/submit`、`push/register` 后端全部就绪，前端无对应 UI。**设备 token 从未注册 → 离线推送链路不成立**。

**整改**：个人页加"举报/拉黑"、设置页加"认证中心"、App 启动注册 push token。

### 3.9 【低】用户模块未接线

相册（photos 增删改查/封面）、隐私设置（settings 页是纯静态菜单，5 项不可点）、搜索、新手引导（onboarding）后端路由全在，前端加页面即可闭环。

### 3.10 【低】社交衍生模块（按版本分批）

圈子 / 游戏 / 破冰话题 / 亲密关系 / 贵族装扮 / 贴纸：后端半新（部分表缺失），前端整体为空。建议**分批接入**，避免一次性铺开。

### 3.11 【低】管理后台

后端约 45 个 admin 路由，`admin.html` 只接了 9 个页面（未接认证审核/敏感词/审核队列/公告/系统配置/管理员/推送/数据统计）。按真实需要补页面，否则删冗余路由。

## 四、视觉/前端问题与整改

### 4.1 【高】双前端文件并存（源头风险）

| | `public/js/yujian-app.js`（运行时） | `public/yujian-app.js`（遗留） |
|---|---|---|
| 行数 | 1058 | 342 |
| 内容 | 最新（chatUp/呼叫/礼物/NotificationUtils/版本号） | 旧版（like/skip，WS 连旧路径） |
| 被引用 | ✅ index.html `?v=...` | ❌ 游离文件 |

**整改**：删除 `public/yujian-app.js`（git 历史可查），杜绝"误把 index.html 引用改回旧文件"的风险。本次未提交改动还在改这个遗留文件——**确认改动目标应是 `public/js/yujian-app.js`**。

### 4.2 【高】双 CSS 体系 + 双变量 + 双 Toast 并存

- **双 CSS**：全量语义类（`.app-header/.btn-primary/.msg-bubble`）与模板缩写别名类（`.app/.hdr/.bp/.bo/.tm/.msg-my/.ci` 等约 100 行）**同一视觉元素两套类名、两处定义**；
- **双变量**：`--primary` 等完整语义变量 + `--p/--w/--b/--tm` 等 16 个缩写别名（为迁就模板内联 `var(--tm)` 临时加的）；
- **双 Toast**：AppRoot 自带旧 toast（38 处 `toast(msg,"terr"/"tok")`，白底黑字）与 notification.js 的渐变 `toast-*` 体系并存，**视觉割裂**。

**整改**：
1. 以 notification.js 的 `.toast-*` 渐变体系为准，删旧 toast 渲染与 `.tm` 类，统一 `NotificationUtils.showToast` 为唯一入口；
2. 高频内联样式逐步迁移为语义类（`var(--tm)`→`.txt-muted`、`var(--w)`→卡片类），**删除/冻结缩写别名层**，只留一套语义类 + 语义变量。

### 4.3 【高】90% 样式内联，无设计系统

**现状**：17 个页面模板约 90% 的样式是 `style="..."` 内联（color/size/margin/border 遍布）。改品牌色/间距/圆角需全文正则替换，无法统一维护；类名缩写不可读（`.bp/.bo/.bs/.bw/.tm/.tp/.ci/.msg-my`），新人无法理解。

**整改**：建立**单一设计规范页**（`docs/design-system.md`），定义色板/间距/圆角/字体/按钮/卡片规范；按页面分批把内联样式迁移为语义类。

### 4.4 【高】品牌色混乱（粉/紫/橙三套并存）

**现状**：CSS 变量 `--primary:#FF5E7D`（粉），但全文件散落硬编码渐变：`#FF6B6B→#FF8E8E`（welcome/my/earnings）、`#667eea→#764ba2`（紫，默认头像/用户主页/发消息按钮）、`#FF6B9D→#FF8E53`（打招呼按钮）、`#FF6B6B→#FF4757`（icon.svg）。**同一 App 三种主视觉**。

**整改**：先定**单一主视觉**（建议粉红系），把硬编码渐变收敛到 2~3 个变量（`--primary` / `--gradient-a` / `--gradient-b`），统一替换。

### 4.5 【中】无骨架屏接入

## 五、部署/安全/测试问题与整改

### 5.1 【高危】密钥入库（必须立即处理）

**已确认**（`git ls-files` 命中）：
- **`yujian.pem`**：阿里云 ECS RSA 私钥，已提交入库（`ccce7ee`）；
- **`deploy-fix.sh`**：明文硬编码生产 MySQL 密码 `Yujian@2024DB`，已入库（`a13ff23`）；
- **`AGENTS.md`**：明文写 MySQL/Redis 密码、ECS IP、GitHub token 拼接示例，已入库。

**整改**：
1. **立即轮换所有泄露凭据**：ECS 密钥对（删旧建新）、MySQL 密码、Redis 密码；检查 GitHub 仓库是否 public；
2. 凭据移出仓库：`git rm --cached` 三个文件 + `.gitignore` 加 `*.pem`；`deploy-fix.sh` 重写为从 env 读；`AGENTS.md` 脱敏；
3. 仓库若公开必须 `git filter-repo` 清历史。

### 5.2 【高危】生产模拟开关

**现状**：`SMS_SIMULATE=true` 时任意手机号 + 固定验证码 `123456` 即可登录。内测默认 sandbox 模式上线，**等于账户可被批量盗取**。

**整改**：确认生产 `SMS_SIMULATE=false`、`SIMULATE_PAYMENT=false`，并加启动护栏。

### 5.3 【中】上传校验缺口

**现状**：头像/动态上传调了 `validateMagicBytes`（读文件头 4 字节），但 `server.js` 的 `/api/upload/image` 与 `/api/upload/voice`（聊天/语音通道）**只过 MIME 白名单，未校验 magic byte**——MIME 可伪造，存在"伪图片"（实际恶意文件）写入风险。

**整改**：两个内联上传路由补调 `validateMagicBytes`。

### 5.4 【中】JWT/WS 鉴权加固

- `auth.js`、`websocket-server.js` 回退 `|| 'your_jwt_secret_key'`，应改为环境缺失即拒绝；
- WS token 走 URL query（进 nginx 日志），改握手 header 或首帧认证；
- 限流依赖 `req.ip`，nginx 反代下 **`trust proxy` 未显式开启**，所有请求可能共享同一限流键——需确认并配置；
- admin 角色仅存于 JWT，提权/降权不即时生效。

### 5.5 【中】schema 双轨 + 人肉迁移

**现状**：`schema.sql`（33 表）与 6+ 个 `src/db/*.sql` 迁移脚本双轨，**19 张表只存在于迁移脚本不在 schema.sql**；迁移无版本号、无 `schema_migrations` 表、无执行顺序；DEPLOY.md 明确"数据库变更手工执行"。新环境按 schema.sql 初始化会缺表；上生产靠人肉记忆执行（历史最高事故源）。

**整改**：建 `schema_migrations` 表 + 迁移脚本编号与顺序；`schema.sql` 与迁移合并为唯一事实源；上线脚本化执行并校验。

### 5.6 【中】无回滚/灰度/制度化备份/告警

| 项 | 现状 |
|---|---|
| 回滚 | 无（代码与库都不行） |
| 灰度 | 无（单实例 fork，cluster 预案未启用） |
| 备份 | DEPLOY.md 有 mysqldump crontab 示例，**未落盘为脚本** |
| 告警 | **完全缺失**，无 webhook/邮件；`logs/error.log` 当前为空文件 |
| 日志 | winston 有结构化 JSON，但无 requestId/traceId，跨请求无法关联 |

**整改**：备份脚本入库 + 恢复演练；错误告警挂 webhook；日志加 requestId；发布打 tag + DB 变更配回滚 SQL；cluster 扩容前先把内存降级替换为 Redis 兜底。

### 5.7 【高】测试体系为零

**现状**：
- `package.json` `"test"` 是占位符（`echo ... && exit 1`），**无任何自动化测试/CI/lint**；
- 4 个手工脚本（`test-api.js` 23 项冒烟等）是黑盒 HTTP 冒烟，要求服务已启动、依赖 `SMS_SIMULATE` 固定验证码，且**会真实写数据污染开发库**；
- 无 `*.test.js` / jest / mocha / vitest。

**整改**：引入 vitest + supertest，把冒烟脚本迁移为**可重复、不污染数据**的测试；`npm test` 接入真实入口 + CI；WS 消息链路的测试补上。

### 5.8 【低】其他清理

- `.venv/`（Python 虚拟环境，Node 项目无用）、`.snapshots/`（Claude 快照残留）、开发过程草稿（`claude-code-complete-tasks.md`/`admin-tasks.md`/`chat-diag.md`）可归档；
- helmet 生产收紧 CSP（去 `unsafe-inline`）；内容审核 fail-open 策略在合规上是风险点，评估 fail-closed。

## 七、开发规范建议（防复发）

1. **最小化改动**：改前端确认运行时文件是 `public/js/yujian-app.js`（不是 `public/yujian-app.js`）；改后端确认 `src/` 版（不是根目录副本）；
2. **单事实源**：同一逻辑只保留一份实现（聊天发送、内存降级、事件常量、错误码、版本号）；
3. **上线 = 测试 + 部署 + 验证**：改完跑 `npm test`（第 3 期后）+ `node --check` 语法检查 + 部署后真机验证（记忆教训：API 正常 ≠ 前端正常）；
4. **凭据永不入库**：`.gitignore` 加 `*.pem`、密钥一律走 env；
5. **schema 变更随代码走**：任何 `ALTER/CREATE` 进迁移脚本并编号，杜绝"手工 ALTER"。
